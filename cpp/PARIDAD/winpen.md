# Pen buttons, ripples and handwriting panel (winpen)

Owner: `app/winpen.*` (Windows-only effects), `SettingsController` (bound buttons), `Editor` (per-button tool mapping while hovering).

## What was decided
1. **Ripple / wave under the pen.** `winpen::applyToWindow` calls `SetWindowFeedbackSetting(hwnd, kind, 0, sizeof(BOOL), &FALSE)` for the 11 feedback kinds (contact visualisation, pen barrel visual, pen tap / double tap / press-and-hold / right tap, touch tap / double tap / press-and-hold / right tap, gesture press-tap). It is loaded with GetProcAddress (Windows 8+, MinGW has no header). An app-wide event filter does it on `Show` / `WinIdChange` of every top-level widget (main window, dialogs, tool box, popups). The tablet service is also answered: a native event filter returns `TABLET_DISABLE_PRESSANDHOLD | PENTAPFEEDBACK | PENBARRELFEEDBACK | TOUCHUIFORCEOFF | TOUCHSWITCH | FLICKS | SMOOTHSCROLLING | FLICKFALLBACKKEYS` for `TabletQuerySystemGestureStatus`, and the same value is stored in the `MicrosoftTabletPenServiceProperty` window property. Nothing else: no registry, no system setting. One owner, so MainWindow::nativeEvent was not touched.
2. **Handwriting panel over text boxes.** Chosen: take away the input-method context of the text inputs (`WA_InputMethodEnabled=false` + `ImhNoPredictiveText|ImhNoTextHandles`) for QLineEdit, QAbstractSpinBox, editable QComboBox, QTextEdit/QPlainTextEdit (the page text tool's editor is a QPlainTextEdit) and their viewports, on `Polish` and again on `FocusIn`. Qt's Windows input context then detaches the IMM/TSF context from the window (`ImmAssociateContext(hwnd, nullptr)`) while such a field has the focus, which is what the pen panel attaches to. Typing is unaffected because dead keys, `ñ`, accents and Alt codes reach Qt as WM_CHAR / key events, not through an IME (the text tool uses `keyPressEvent`, no `inputMethodEvent`). Cost: no IME composition (Chinese/Japanese/Korean, Windows emoji/handwriting insertion) in the app's fields. Rejected: `ImmDisableIME` for the thread (too broad, also fights Qt, which re-associates contexts on every focus change) and any registry/TabTip setting (forbidden).
3. **Hold-to-use buttons** and **hover tool while a Preferencias button is held**: see `app/API.md` (last section).
   * Driver sending the barrel as mouse Right/Middle/Back/Forward: middle/back/forward bound to a tool use the same hold (press selects, release gives back). Right-click is not bindable (as before); its tool comes from Preferencias > Ratón and, as a gesture, is already "only while held".

## Verified (offscreen `--selftest`, synthetic QTabletEvent/QMouseEvent through the window event path)
Barrel press with hover -> hand, move, release -> previous tool; tip down with button held drags with the hand and the tool comes back after the drag; press mid-stroke does not corrupt the stroke; button picked-tool-meanwhile stays; non-tool command once; capture of a barrel button; leave proximity / window deactivate / application inactive clear the hold; middle-click hold; Preferencias mapping while hovering (barrel 2, eraser end), release and proximity; text inputs have no IM context, re-quieted on focus, typed n-tilde/accents arrive. Existing mouse test updated: a bound back button is now held, not permanent.
Also checked outside the app, on the real `windows` platform, with a throwaway program (see the report): `GetWindowFeedbackSetting` reads back FALSE for the kinds Windows accepts, the window property and the query message answer.

## NOT verified: a-probar-por-el-usuario (needs the real pen / driver)
* That the ripple is really gone with the XP-Pen X3 Pro under Windows Ink, and that no other layer (driver overlay) draws one.
* That the handwriting panel no longer pops up on pen click in the text box / line edits. Windows may still show it if Windows' own "show the handwriting panel when no keyboard is attached" is on: the fallback is Settings > Devices > Pen & Windows Ink (not touched by the app).
* That the barrel buttons really arrive as `TabletPress/Release` with `Qt::RightButton` / `Qt::MiddleButton` (also while hovering) in Qt 6 on Windows Ink, and that release is reported when the pen leaves range.
* Driver-mode behaviour (advice, not verified): in the XP-Pen driver set each pen button to "Mouse button" (Right click / Middle click) or leave the default so the app receives it (a key-combo mapping arrives as a keyboard shortcut, which is a key press, with no hold); "Windows Ink" on gives pressure and the barrel through WM_POINTER (what Qt 6 uses), off makes the driver speak WinTab/mouse and the pen then arrives as a mouse (no pressure, no hover buttons); do not use a driver-side "hold to switch tool" macro together with the app's hold.

## Real-pen reports 3 (hand tool, tool box, wheel)
* Cause of "hand scrolls only while hovering": the driver also sends a real mouse middle/right click while the pen is near; `DocumentView::mousePressEvent` took it for the mouse's middle-button pan (Preferencias > Ratón) and panned on hover moves, while the tablet events (tip down) never saw the button. Fixed at the owner: that click is the pen's barrel button (see `app/API.md`, "Real-pen input fixes"); the hand tool only drags with the tip down.
* Cause of the tool box closing on a pen tap: tablet/touch presses reach the application filter as events of the QWindow, `qobject_cast<QWidget*>` gave null and `outsidePress(nullptr)` closed the box. Now decided from the global position.
* Wheel over combos / spin boxes / sliders no longer changes them without the keyboard focus (one app-wide filter).
* Selftests (`app/settings/inputfixselftest.cpp`): barrel as mouse click (hover, drag, re-land, stale states, double report, real mouse unchanged), raw trace, pen taps on the tool box (Editar, Listo, tool button, outside, window-level tablet event) and on a dialog combo with its list, wheel (unfocused/focused combo, spin, slider, line edit of a spin box, page, ACK05 dial, Lapiz y tableta).
* NOT verified (needs the real pen): that the XP-Pen driver really sends the barrel as a mouse click besides (or instead of) tablet buttons (the raw trace in Lápiz y tableta shows it: paste it), and the real Windows tablet-to-mouse synthesis path for taps on dialogs.
* "Botón central del ratón" at the bottom of the canvas is not drawn by this app (the string exists only in the Xournal++ reference translation, source-track/xournalpp/po/es.po): it is a window or label of Xournal++ or of the driver, not a stray overlay of our dialogs.
* Where the test sheet is: Herramientas > Lápiz y tableta... (or the arrow of the pen button's menu, or Preferencias > Lápiz > Probar el lápiz...): "Hoja de prueba" with the readout above it and the raw-input trace.

* **Contact with a barrel button held (XP-Pen, Windows Ink; seen on the real pen).** Qt sends no press when the tip lands with Right/Middle already down, only TabletMove with pressure > 0 and buttons == Right/Middle (no Left). DocumentView::tabletEvent now defines contact once (Left, or raw pressure > 0 with a barrel bit) and starts the gesture on that rising edge (arrelContact_), ends it when pressure returns to 0, on release or on proximity leave; a barrel press during a Left stroke changes nothing. Selftests: 'contact:' checks (Right/Middle x mapped/bound).
